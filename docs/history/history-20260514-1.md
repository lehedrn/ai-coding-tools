## claude-md-management 插件分析

### 插件结构

```
claude-md-management/
├── .claude-plugin                      # 插件元信息
├── LICENSE
├── README.md
├── commands/
│   └── revise-claude-md.md            # 命令：从会话中提取学习更新 CLAUDE.md
├── skills/
│   └── claude-md-improver/
│       ├── SKILL.md                    # 技能：审计 CLAUDE.md 质量
│       └── references/
│           ├── quality-criteria.md     # 质量评分标准（6 维度 100 分制）
│           ├── templates.md            # CLAUDE.md 模板（按项目类型）
│           └── update-guidelines.md    # 更新指南（加什么/不加什么）
├── claude-md-improver-example.png
└── revise-claude-md-example.png
```

### 两个核心功能

| 功能 | 类型 | 触发场景 | 做什么 |
|------|------|---------|--------|
| **claude-md-improver** | Skill | 用户要求审计/检查 CLAUDE.md | 扫描所有 CLAUDE.md → 按 6 维度评分 → 输出质量报告 → 提议针对性更新 |
| **/revise-claude-md** | Command | 会话中发现 CLAUDE.md 缺少上下文 | 回顾本次会话 → 找到 CLAUDE.md 文件 → 草拟简洁补充 → 展示 diff → 用户确认后应用 |

### 质量评分体系（100 分制）

| 维度 | 分值 | 重点 |
|------|------|------|
| 命令/工作流 | 20 | 构建/测试/部署命令是否存在 |
| 架构清晰度 | 20 | 目录结构、模块关系、入口点 |
| 非明显模式 | 15 | 坑点、workaround、边界情况 |
| 简洁性 | 15 | 无冗余、每行有价值 |
| 时效性 | 15 | 反映当前代码库状态 |
| 可操作性 | 15 | 命令可直接复制执行 |

### 核心设计原则

1. **CLAUDE.md 是 prompt 的一部分** — 上下文窗口宝贵，每行都要挣到它的位置
2. **只加项目特定的** — 通用建议（"写测试"、"用有意义的变量名"）不加
3. **简洁一行一概念** — `<命令/模式> - <简短说明>`
4. **区分共享/个人** — `CLAUDE.md` 团队共享（提交 git），`.claude.local.md` 个人本地（gitignore）
5. **更新前先输出报告** — 不直接改，先评分、列问题、提议 diff，用户确认后才改

### 与本项目 init-claude-md 的对比

| 维度 | init-claude-md | claude-md-management |
|------|---------------|---------------------|
| **定位** | 从零初始化 CLAUDE.md | 维护/改进已有 CLAUDE.md |
| **时机** | 项目首次使用 Claude Code 时 | 项目演进中持续维护 |
| **输入** | 扫描项目结构 + 交互讨论 | 当前代码库状态 + 会话学习 |
| **输出** | 完整的 CLAUDE.md + info.md | 质量报告 + 针对性 patch |
| **质量标准** | 可操作/可验证/不过时 | 6 维度 100 分评分体系 |
| **更新方式** | 整体生成 | diff 式增量更新 |

**互补关系**：`init-claude-md` 解决"从无到有"，`claude-md-management` 解决"从有到好"。两者不冲突，可以共存。

### 值得借鉴的点

1. **质量评分体系** — 我们的 init-claude-md 有"质量三标准"但缺乏量化评分，6 维度 100 分制更客观
2. **`.claude.local.md` 机制** — 个人偏好放本地文件、gitignore，与团队共享的 CLAUDE.md 分离
3. **diff 式更新** — revise-claude-md 用 diff 展示变更，比整文件重写更清晰
4. **更新指南中的"不加什么"** — 明确反模式（显而易见的信息、通用建议、一次性修复、冗长解释），我们当前缺少这部分
5. **多层级 CLAUDE.md** — 根目录、子目录、包目录、全局 `~/.claude/CLAUDE.md`，支持 monorepo

### 1. 增加"反模式"警告（推荐采纳）

**现状**：SKILL.md 告诉 AI 写什么，但没明确说"不写什么"，容易导致 CLAUDE.md 膨胀。

**改进**：在 SKILL.md 的核心原则中补充"不加什么"清单：

```

- 显而易见的信息（UserService 处理用户操作 — 类名已说明）
- 通用最佳实践（"写测试"、"用有意义的变量名"）
- 一次性修复记录（"修复了 commit abc123 的 bug"）
- 冗长解释（JWT 的 RFC 编号、算法原理等）
```

**理由**：成本低、收益高，直接防止 CLAUDE.md 变成文档垃圾场。

---

### 2. 引入 `.claude.local.md` 个人文件（推荐采纳）

**现状**：所有偏好都写入 `CLAUDE.md`，但有些是个人偏好（回复语言、详细度），有些是团队共识（代码风格、架构约定），混在一起。

**改进**：
- `CLAUDE.md` — 团队共享，提交 git
- `.claude.local.md` — 个人/本地，加入 `.gitignore`

init-claude-md 在第 3 步交互讨论时，区分哪些章节放共享、哪些放本地。比如：
- 回复风格 → `.claude.local.md`（个人偏好）
- 代码风格 → `CLAUDE.md`（团队共识）
- 协作偏好 → `.claude.local.md`（个人偏好）

**理由**：多人协作时避免个人偏好污染团队文件，也能让不同开发者有各自的 AI 交互风格。

**疑问**：当前项目是你个人使用为主，是否现在就需要这个区分？

---

### 3. 质量三标准 + 评分体系（可选采纳）

**现状**：输出前自检"可操作/可验证/不过时"三标准，是定性判断。

**改进**：借鉴 6 维度评分，但简化为 4 维度（去掉架构清晰度和非明显模式，因为 init 阶段这些信息还没积累）：

| 维度 | 分值 | 检查内容 |
|------|------|---------|
| 可操作性 | 30 | 命令能直接复制执行 |
| 简洁性 | 25 | 无冗余、每行有价值 |
| 时效性 | 25 | 不放版本号等易变信息 |
| 项目特定性 | 20 | 非通用建议 |

**理由**：量化标准让自检更客观，但也可能让初始化流程变重——init 阶段本来就是在交互中确认的，评分的意义不如审计阶段大。

**我的倾向**：暂不加评分，保留三标准自检。等以后如果有"审计已有 CLAUDE.md"的需求（类似 claude-md-improver），再引入评分体系。
