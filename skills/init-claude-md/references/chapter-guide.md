# 章节交互指引

本文档为 init-claude-md Skill 各章节的详细交互规范。Skill 执行第 3 步时，按本文档逐章与用户交互。

## 3.1 项目概述

**目的**：让 AI 理解项目是什么、为什么存在。

**交互方式**：一次性提问所有问题，用户回答后起草内容。

**需要回答的问题**：
1. 项目名称和一句话定位是什么？
2. 项目从零开始还是基于现有代码？是否有参考项目？
3. 当前处于什么阶段（规划/开发/维护）？

**起草要求**：
- 用一段话概括，不超过 3 句
- 必须包含项目名称和核心定位
- 如果有参考项目，简要说明关系

**示例输出**：
```markdown
my-boot 是一个从零到一构建的基础开发平台。项目通过分析若依（RuoYi）和 BladeX 两个开源框架，吸取各自精华，结合自身需求与定位，打造适配自身业务的基础平台，为后续服务开发奠定基础。
```

## 3.2 回复风格

**目的**：定义 AI 的沟通方式，减少来回澄清。

**交互方式**：用 AskUserQuestion 工具一次性提问，提供选项降低思考成本。

**需要回答的问题**：
1. 回复使用什么语言？
2. 代码标识符、技术术语保持原文还是翻译？
3. 倾向于简洁回答还是详细展开？
4. 是否需要 AI 主动展示细节，还是等追问？

**常见选项**：

| 维度 | 选项 A | 选项 B | 选项 C |
|------|--------|--------|--------|
| 语言 | 中文 | 英文 | 混合（日常中文，术语英文） |
| 详细度 | 简洁：只给结论，需要时再展开 | 详细：主动展示所有细节 | 按语境：简单问题简洁，复杂问题详细 |

**起草要求**：
- 每条规则必须可操作，AI 读完知道怎么做
- 如果用户选"混合"或"按语境"，需要写明判断标准

**示例输出**：
```markdown
### 回复风格
- 主动展示所有细节，不需要用户追问就展开完整说明
- 回复使用中文，代码标识符保持英文原样
```

## 3.3 代码风格

**目的**：让 AI 生成的代码符合项目规范，减少 review 成本。

**交互方式**：用 AskUserQuestion 工具提问，提供选项。

**需要回答的问题**：
1. 代码注释使用什么语言？
2. 是否有设计原则偏好？
3. 错误处理策略？
4. 是否有特殊代码规范？（命名、格式、禁止事项）
5. 是否有只读目录或特殊路径约定？

**常见选项**：

| 维度 | 选项 A | 选项 B | 选项 C |
|------|--------|--------|--------|
| 设计原则 | YAGNI：不提前引入不需要的依赖 | KISS：保持简单 | 不过度设计 |
| 错误处理 | 最小化：只处理必要的 | 防御性：对所有外部输入做校验 | — |
| 代码创建 | 优先编辑现有文件 | 优先创建新文件 | — |

**起草要求**：
- 规则必须可验证（如"不过度设计"太模糊，应细化为"不提前引入不需要的模块或依赖"）
- 只写用户确认的规则，不自行补充

**示例输出**：
```markdown
### 代码风格
- 不过度设计，优先编辑现有文件而非创建新文件
- 代码注释使用中文
- 不加多余的错误处理或向后兼容 hack
- 功能按需添加，不要提前引入不需要的模块或依赖（YAGNI）
- `sources/` 目录是参考学习的只读资料，不可修改；所有自有代码写在项目根目录下
```

## 3.4 协作偏好

**目的**：定义 AI 的行动边界，防止越权操作。

**交互方式**：用 AskUserQuestion 工具提问，提供选项。

**需要回答的问题**：
1. AI 是否可以先执行再汇报，还是必须先讨论后执行？
2. 哪些操作需要确认？
3. 是否允许 AI 主动建议？建议后如何推进？
4. 上下文是否需要跨会话连贯？

**常见模式**：

| 维度 | 选项 A | 选项 B | 选项 C |
|------|--------|--------|--------|
| 执行模式 | 先执行后汇报 | 先讨论后执行 | 混合：低风险自主，高风险需确认 |
| 建议 | 允许主动建议，经同意后推进 | 不主动建议，等用户指示 | — |

**起草要求**：
- 用粗体标题强调关键规则，便于 AI 快速识别
- "先讨论后执行"要写明讨论到什么程度算确认

**示例输出**：
```markdown
### 协作偏好
- **讨论优先**：方案先讨论，未经确认不执行
- **不擅自行动**：不擅自删除/引入/优化
- **主动建议**：可主动建议，经同意后推进
- **上下文连贯**：基于已有文档和结论工作，不脱离基础重来
```

## 3.5 文档规范（可选）

**目的**：定义 AI 协助写文档的写入规则。

**交互方式**：先询问是否需要此章节，需要则继续提问。

**需要回答的问题**：
1. 文档存放在哪个目录？
2. 是否有单文件大小限制？
3. 大文档是否需要拆分？拆分策略？
4. 文件命名规范？
5. 文档更新策略？

**起草要求**：
- 限制条件必须写具体数值（如"200 行"而非"不要太大"）
- 更新策略要写明触发条件（如"执行操作后主动思考是否需更新"）

**示例输出**：
```markdown
## 文档规范

**更新策略：** 执行操作后主动思考是否需更新文档，如需要则按写入规范执行

**写入规范：**
- 单次写入超过 200 行时，分段完成（每次 100-200 行）
- 文档内容过大时，先按主题或模块拆分为分文档，依次写入
- 拆分后的文档通过索引文档组织，避免上下文丢失

**命名规范：**
- 文件名、目录名使用小写字母，单词间用连字符 `-` 连接
- 不要使用空格，中文文件名允许（如 `01-概述.md`）
```

## 3.6 自定义章节（可选）

**目的**：上述章节未覆盖的项目特殊需求。

**交互方式**：列出引导问题，用户可以选择添加哪些。

**引导问题**：
1. 是否有特殊的测试要求？
2. 是否有 Git 工作流规范？
3. 是否有部署/安全相关的约束？
4. 还有什么想让 AI 知道的项目约定？

**起草要求**：
- 每个自定义章节需要有明确的标题
- 内容格式与前面章节保持一致：可操作、可验证
